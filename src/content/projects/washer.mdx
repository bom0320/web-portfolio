- 운영 중 발생한 문제 대응
- 기존 코드 리팩터링 및 유지보수

### 주요 기술

`Next.js` · `React` · `TypeScript` · `TanStack Query` · `Zustand` · `Zod`

<ProjectDetailSection
  id="skills"
  eyebrow="02 · ENGINEERING"
  title="서버 상태와 UI 상태의 책임을 분리했습니다."
>
초기 코드에서는 API 요청과 화면 상태를 구분하지 않고 처리하는 부분이 존재했습니다.

화면이 복잡해질수록 같은 데이터를 여러 곳에서 다시 요청하거나,
서버에서 받아온 값을 컴포넌트 내부 상태로 복사하는 코드가 늘어났습니다.

예를 들어 다음과 같은 형태입니다.

```tsx
const [machines, setMachines] = useState<Machine[]>([]);
const [isLoading, setIsLoading] = useState(false);

useEffect(() => {
  const fetchMachines = async () => {
    setIsLoading(true);

    const response = await api.get("/machines");

    setMachines(response.data);
    setIsLoading(false);
  };

  fetchMachines();
}, []);
```

작은 화면에서는 문제가 없지만 같은 데이터가 여러 화면에서 필요해지면서
요청 시점과 캐시 상태를 각각 관리해야 했습니다.

그래서 서버에서 가져오는 상태는 `TanStack Query`,
클라이언트에서만 필요한 상태는 `Zustand`로 역할을 구분했습니다.

```ts
export const machineKeys = {
  all: ["machines"] as const,

  list: () => [...machineKeys.all, "list"] as const,

  detail: (machineId: number) =>
    [...machineKeys.all, "detail", machineId] as const,
};
```

```ts
export const useMachinesQuery = () =>
  useQuery({
    queryKey: machineKeys.list(),
    queryFn: getMachines,
    staleTime: 1000 * 60,
  });
```

Mutation 이후에는 관련 Query만 무효화하도록 정리했습니다.

```ts
const updateMachineMutation = useMutation({
  mutationFn: updateMachine,

  onSuccess: (_, variables) => {
    queryClient.invalidateQueries({
      queryKey: machineKeys.detail(variables.machineId),
    });

    queryClient.invalidateQueries({
      queryKey: machineKeys.list(),
    });
  },
});
```

이렇게 변경하면서 컴포넌트는 데이터를 **어떻게 저장할지**보다
**어떤 데이터를 보여줄지**에 집중할 수 있게 했습니다.

![관리 화면 구조](/images/projects/washer/detail-02.png)

### 상태의 책임

| 상태        | 관리 방식             | 이유          |
| ----------- | --------------------- | ------------- |
| 세탁기 목록 | TanStack Query        | 서버 데이터   |
| 예약 정보   | TanStack Query        | 서버 데이터   |
| 사용자 정보 | TanStack Query        | 서버 데이터   |
| 필터 상태   | Zustand / Local State | UI 상태       |
| 모달 상태   | Local State           | 컴포넌트 상태 |

이를 통해 동일한 사용자 시나리오에서 발생하던 API 요청을 줄이고,
데이터 흐름을 한 곳에서 추적할 수 있도록 구조를 정리했습니다.

<ProjectDetailSection
  id="trouble-shooting"
  eyebrow="03 · TROUBLE SHOOTING"
  title="API 응답을 그대로 신뢰하지 않도록 변경했습니다."
>
TypeScript를 사용하고 있었지만 실제 API 응답은 런타임에 들어옵니다.

즉 아래 타입은 개발 단계에서는 안전해 보여도,

```ts
type User = {
  id: number;
  name: string;
  penaltyCount: number;
};
```

실제 서버가 다음 값을 보내는 상황을 막아주지는 못합니다.

```json
{
  "id": 12,
  "name": "Kim Bom",
  "penaltyCount": null
}
```

기존에는 API 타입과 화면에서 사용하는 타입이 동일하다고 가정했기 때문에
예상하지 못한 `null` 값이 들어오면 UI 깊은 곳에서 문제가 발생했습니다.

그래서 API 응답과 UI 모델 사이에 검증 단계를 추가했습니다.

```ts
import { z } from "zod";

export const UserResponseSchema = z.object({
  id: z.number(),
  name: z.string(),
  penaltyCount: z.number().nullable(),
});
```

API에서 데이터를 받은 직후 검증합니다.

```ts
export const getUser = async (userId: number) => {
  const response = await api.get(`/users/${userId}`);

  return UserResponseSchema.parse(response.data);
};
```

그리고 화면에서는 Mapper를 거쳐 필요한 형태로 변환합니다.

```ts
export const mapUserResponse = (response: UserResponse): User => ({
  id: response.id,
  name: response.name,
  penaltyCount: response.penaltyCount ?? 0,
});
```

전체 흐름은 다음과 같이 변경했습니다.

```text
API Response
     ↓
  unknown
     ↓
Zod Validation
     ↓
     DTO
     ↓
   Mapper
     ↓
 UI Model
```

> 타입 선언만으로 API 계약이 지켜진다고 가정하지 않고,
> 외부 데이터가 애플리케이션 내부로 들어오는 경계에서 검증하도록 변경했습니다.

![API 데이터 처리 구조](/images/projects/washer/detail-03.png)

### 문제를 발견한 방식

1. 특정 사용자 데이터에서만 화면 오류 발생
2. Network Response와 TypeScript DTO 비교
3. 일부 필드에서 `null` 응답 확인
4. 다른 API Response까지 동일한 문제 조사
5. 주요 API 응답에 Runtime Validation 적용

이 과정에서 단순히 문제가 발생한 필드만 수정하는 대신,
**같은 유형의 문제가 다시 발생할 수 있는 경계를 찾아 구조적으로 처리하는 것**에 집중했습니다.

### 주요 변화

| Before                      | After                  |
| --------------------------- | ---------------------- |

특히 관리자 페이지는 기능이 추가될 때마다 코드가 커지고 있었기 때문에,
단순히 컴포넌트 몇 개를 분리하는 것보다
**어떤 변경 이유를 기준으로 코드를 나눌 것인지**를 먼저 결정했습니다.

```ts
type ApiError =
  | "UNAUTHORIZED"
  | "FORBIDDEN"
  | "NOT_FOUND"
  | "VALIDATION"
  | "CONFLICT"
  | "NETWORK"
  | "SERVER"
  | "UNKNOWN";
```

서로 다른 API 요청에서 발생하던 에러도
UI가 처리할 수 있는 공통 형태로 변환했습니다.

```ts
export function normalizeApiError(error: unknown): ApiError {
  if (isAxiosError(error)) {
    if (!error.response) {
      return "NETWORK";
    }

    switch (error.response.status) {
      case 401:
        return "UNAUTHORIZED";

      case 403:
        return "FORBIDDEN";

      case 404:
        return "NOT_FOUND";

      case 409:
        return "CONFLICT";

      default:
        return "SERVER";
    }
  }

  return "UNKNOWN";
}
```
