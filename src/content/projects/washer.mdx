기능이 지속적으로 추가되면서 관리자 화면 내부의 책임도 함께 커졌습니다.

관리자는 기기 상태를 확인하고, 예약을 확인하고,
사용자 패널티와 고장 신고를 각각 다른 흐름에서 처리해야 했습니다.

### 문제 1. 정보가 여러 기능에 분산됨

하나의 상황을 확인하기 위해 여러 화면을 이동해야 했습니다.

```text
고장 신고 확인
      ↓
기기 정보 확인
      ↓
현재 예약 확인
      ↓
사용자 정보 확인
      ↓
처리
```

### 문제 2. 데이터 요청의 책임이 불분명함

화면 단위로 API 요청이 추가되면서
같은 서버 데이터를 여러 컴포넌트에서 각각 가져오는 코드가 생겼습니다.

```tsx
useEffect(() => {
  getMachines().then(setMachines);
}, []);

useEffect(() => {
  getReservations().then(setReservations);
}, []);
```

기능 자체는 동작했지만,
어떤 데이터가 어디에서 관리되는지 추적하기 어려워졌습니다.

> 기능이 많아지는 것보다 더 큰 문제는
> 변경이 발생했을 때 어느 코드까지 영향을 받는지 알기 어려워지는 것이었습니다.

관리자 화면은 기능의 수보다 **정보를 어떤 순서로 확인하는가**가 중요했습니다.

그래서 각 화면을 독립적인 기능 목록으로 보기보다,
실제 운영 과정에서 관리자가 수행하는 작업을 기준으로 다시 확인했습니다.

### 관리 흐름

1. 현재 운영 상태 확인
2. 문제가 있는 기기 확인
3. 예약 상황 확인
4. 사용자 정보 확인
5. 필요한 조치 수행

```text
Dashboard
   ↓
Machines
   ↓
Reservations
   ↓
Users / Reports
```

UI에서도 중요한 정보와 보조 정보의 우선순위를 구분했습니다.

### 화면에서 고려한 기준

- 현재 상태를 빠르게 인지할 수 있는가
- 문제 발생 위치를 쉽게 찾을 수 있는가
- 다음 행동을 예측할 수 있는가
- 반복적인 이동을 줄일 수 있는가

![Experience Test](/images/projects/washer/detail-03.png)

실제 콘텐츠 확정 단계에서는 이 부분을
사용자 경험 개선 사례와 화면 비교 이미지로 교체하면 됩니다.

<ProjectDetailSection
  id="engineering"
  eyebrow="04 · ENGINEERING"
  title="변경을 추적할 수 있는 구조로 정리했습니다."
>
화면 구조뿐 아니라 데이터의 책임도 함께 정리했습니다.

서버에서 가져오는 데이터는 `TanStack Query`,
화면에서만 필요한 상태는 local state 또는 client state로 구분했습니다.

### Query Key 관리

```ts
export const machineKeys = {
  all: ["machines"] as const,

  list: () => [...machineKeys.all, "list"] as const,

  detail: (machineId: number) =>
    [...machineKeys.all, "detail", machineId] as const,
};
```

Mutation 이후에는 영향을 받은 Query만 무효화합니다.

```ts
const mutation = useMutation({
  mutationFn: updateMachine,

  onSuccess: (_, variables) => {
    queryClient.invalidateQueries({
      queryKey: machineKeys.detail(variables.machineId),
    });
  },
});
```

### API Response 검증

TypeScript 타입 선언만으로는 실제 서버 응답을 보장할 수 없습니다.

```ts
const UserResponseSchema = z.object({
  id: z.number(),
  name: z.string(),
  penaltyCount: z.number().nullable(),
});
```

데이터가 애플리케이션 내부로 들어오는 경계에서 검증합니다.

```text
API Response
     ↓
   unknown
     ↓
Zod Validation
     ↓
    DTO
     ↓
  Mapper
     ↓
 UI Model
```

| Before                    | After                 |

| 하나의 거대한 관리자 화면 | 역할별 5개 화면       |

| 화면마다 다른 오류 처리   | 공통 오류 모델        |

<ProjectDetailSection
  id="retrospective"
  eyebrow="06 · RETROSPECTIVE"
  title="좋은 구조는 변경을 예측할 수 있게 합니다."
>
프로젝트를 시작했을 때는 구조를 잘 만든다는 것을
컴포넌트와 파일을 잘게 나누는 것이라고 생각했습니다.

하지만 실제 운영 중인 서비스를 유지보수하면서
구조의 목적은 코드의 모양보다 **변경이 발생했을 때 영향을 예측할 수 있게 만드는 것**에 가깝다는 것을 배웠습니다.

### 이후 확인하는 질문

- 지금 해결하려는 문제는 무엇인가?
- 이 데이터의 주인은 누구인가?
- 서버 상태와 UI 상태가 구분되어 있는가?
- 외부 데이터는 어느 경계에서 검증하는가?
- 오류가 발생했을 때 어느 계층이 책임지는가?
- 새로운 요구사항이 추가되면 어디를 수정해야 하는가?

```ts
function designBeforeImplementing() {
  return {
    problem: "무엇을 해결하는가",
    responsibility: "누가 책임지는가",
    boundary: "어디에서 검증하는가",
    change: "무엇이 바뀔 수 있는가",
  };
}
```
