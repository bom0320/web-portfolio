kimbom.dev는 프로젝트를 나열하기 위한 포트폴리오가 아니라, **제가 어떤 문제에 관심을 가지고 어떤 방식으로 만드는 사람인지 하나의 웹 경험으로 전달하기 위해 직접 기획·디자인·개발한 개인 웹사이트입니다.**

사이트를 만들기 전, 먼저 **어떤 개발자로 기억되고 싶은지와 제가 중요하게 생각하는 작업 방식을 정의했습니다.** 이를 소개 문구로 설명하는 데 그치지 않고, 사용자가 어떤 정보를 먼저 보고 무엇을 기준으로 다음 내용을 이해해야 하는지까지 고려해 정보 구조와 화면의 흐름을 설계했습니다.

또한 디자인의 의도가 실제 경험으로 이어지도록 스크롤과 인터랙션을 활용해 장면을 구성하고, 프론트엔드 구현까지 직접 연결했습니다. 배포 이후에는 처음 설계한 경험을 그대로 유지하기보다 **사용자 피드백과 행동 데이터, 성능 지표를 기준으로 전달 방식과 구현을 지속적으로 개선하고 있습니다.**

저의 가장 강한 기술적 기반은 Frontend Engineering입니다. 하지만 실제 프로젝트에서는 화면을 구현하는 한 단계만 보기보다, **어떤 경험이어야 하는지 정의하는 것부터 정보 구조와 인터랙션, 코드 구조와 성능, 그리고 배포 이후 사용자의 반응을 확인하고 다시 개선하는 과정까지 함께 다뤄왔습니다.**

`Frontend Engineer`라는 직무명은 제가 가진 기술적 기반을 설명할 수 있지만, **어떤 범위까지 문제를 바라보고 어떤 기준으로 결과물을 만드는 사람인지는 충분히 보여주기 어려웠습니다.** 다른 직무명을 덧붙이거나 소개 문장을 길게 만드는 것 역시 같은 한계가 있다고 생각했습니다.

그래서 kimbom.dev에서는 제가 어떤 사람인지 말로 설명하는 데 그치지 않고, **사이트 자체가 제가 중요하게 생각하는 기준과 작업 방식을 보여주는 하나의 증거가 되도록 설계했습니다.**

이를 위해 세 가지 문제를 함께 해결해야 했습니다.

> **01. 전달의 문제**
>
> 내가 어떤 방식으로 만드는 사람인지 **웹 경험 자체에서 어떻게 느끼게 할 것인가**

> **02. 구현의 문제**
>
> 그 경험을 만들기 위해 생긴 복잡한 인터랙션을 **어떻게 엔지니어링할 것인가**

> **03. 검증의 문제**
>
> 내가 그렇게 설계했다고 주장하는 데서 끝나지 않고 **실제 사용자와 성능 데이터로 어떻게 검증할 것인가**

<span id="experience-positioning" className="project-detail-section__anchor" />

사이트를 만들기 전, 먼저 **어떤 방식으로 만드는 사람으로 기억되고 싶은지**를 정리했습니다.

저의 기술적 기반은 Frontend Engineering이지만, 보여주고 싶었던 것은 직무명 자체보다 **디자인의 의도와 기술적인 구조를 연결하고, 사용자가 실제로 경험하는 과정까지 함께 판단하는 사람**이라는 점이었습니다.

문제는 이 포지셔닝을 소개 문구에 적는 것만으로는 제가 중요하게 생각하는 작업 방식을 충분히 보여줄 수 없다는 것이었습니다. 그래서 **사이트 자체가 같은 관점과 기준으로 동작해야 한다고 판단했습니다.**

이 과정에서 인터랙션을 어떻게 설계할지 고민하며 Apple의 *Designing Fluid Interfaces*를 참고했습니다. 여기서 인상 깊었던 것은 특정 애니메이션 기법이 아니라, **움직임을 단순한 시각 효과가 아니라 사용자의 행동과 상태 변화를 연결하는 인터페이스의 행동으로 바라보는 관점**이었습니다.

특히 좋은 인터페이스는 단순히 부드럽게 움직이는 것이 아니라, **사용자의 입력에 자연스럽게 반응하고 상태가 변하는 과정에서도 이전의 맥락을 잃지 않으며, 다음 변화를 예측할 수 있게 해야 한다는 점**에 주목했습니다.

이를 바탕으로 kimbom.dev에서 사용할 경험의 판단 기준을 다시 정리했습니다.

| Principle      | kimbom.dev에서의 판단 기준                   |
| -------------- | -------------------------------------------- |
| **Hierarchy**  | 무엇을 가장 먼저 보여줄 것인가               |
| **Anchor**     | 화면이 변해도 무엇을 기준으로 남겨둘 것인가  |
| **Motion**     | 왜 움직여야 하는가                           |
| **Continuity** | 이전 상태를 다음 장면과 어떻게 이어갈 것인가 |
| **Adaptation** | 환경이 달라져도 무엇을 유지할 것인가         |

이후 화면과 인터랙션을 설계할 때도 `어떤 효과를 넣을 것인가`보다 **무엇을 먼저 보여줄지, 무엇을 남겨둘지, 왜 움직여야 하는지, 그리고 다음 상태와 어떻게 이어져야 하는지**를 먼저 판단했습니다.

> **사용자의 행동과 정보의 흐름이 분리되지 않고, 현재 무엇을 보고 있으며 다음에 무엇이 일어나는지 자연스럽게 이해할 수 있는 경험을 만들고자 했습니다.**

이 원칙은 이후 정보의 위계와 장면 구성, 모션, 반응형 경험을 판단하는 공통 기준으로 사용했습니다.

<h3 id="experience-hierarchy">
  02. 무엇을 먼저 보여주고, 무엇을 남겨둘지 설계했습니다.
</h3>

앞서 세운 원칙 중 하나는 **화면이 변하더라도 사용자가 현재의 맥락을 잃지 않게 하는 것**이었습니다. 그래서 각 구간을 설계할 때 단순히 콘텐츠를 순서대로 배치하기보다, **한 장면을 통째로 넘길지, 현재 장면을 유지한 채 정보를 단계적으로 보여줄지**부터 판단했습니다.

사이트에 처음 접근하는 구간에서는 역할이나 기술, 프로젝트를 바로 나열하기보다 **먼저 제가 어떤 사람인지에 대한 인상을 만들고, 이후 구체적인 자기소개로 이어지도록** 구성했습니다. 문장과 시각적인 이미지, 자기소개가 각각 분리된 정보라기보다 하나의 인상을 단계적으로 형성하는 과정이라고 봤기 때문입니다.

따라서 화면을 계속 새로 넘기지 않고 같은 시야 안에서 내용이 변화하도록 했습니다. **앞에서 형성된 인상을 다음 정보까지 이어가며, 하나의 이야기처럼 받아들일 수 있도록 하기 위해서였습니다.**

작업 방식을 설명할 때도 하나의 주장을 단계적으로 쌓는 동안에는 **중심이 되는 맥락을 남기고 그 안에서 필요한 정보만 순차적으로 변화**시켰습니다. 반대로 설명이 끝나고 서로 독립적으로 읽어야 하는 내용이 시작되면 고정을 풀어 다시 스크롤의 흐름을 이어갔습니다.

즉 어떤 요소를 `Pin`할지를 먼저 정한 것이 아니라, **정보끼리 어떤 관계를 가지고 있는지를 먼저 판단한 뒤 장면의 유지와 전환 방식을 결정했습니다.**

> **같은 맥락에서 이해해야 하는 정보는 장면 안에서 이어 보여주고, 맥락이 달라지는 순간에는 다음 장면으로 넘겼습니다.**

<h3 id="experience-motion">
  03. 움직임을 효과가 아니라 장면의 행동으로 설계했습니다.
</h3>

모든 애니메이션을 스크롤 위치에 그대로 종속시키지는 않았습니다. 특히 작업 방식이나 핵심 설명처럼 **사용자가 다시 돌아와 읽을 가능성이 높은 내용은, 역스크롤할 때 요소가 다시 사라지거나 이전 상태로 돌아가는 동작이 오히려 읽는 흐름을 방해할 수 있다고 판단했습니다.**

그래서 이런 구간은 한 번 나타난 정보를 그대로 유지했습니다. 반면 첫 화면처럼 **스크롤의 위치 자체가 장면의 진행을 의미하는 전환에서는**, 위로 돌아갔을 때 이전 장면도 함께 복원되도록 설계했습니다.

> **스크롤 방향에 맞춰 무조건 되감기보다, 사용자가 다시 돌아왔을 때 무엇을 하려는지를 기준으로 움직임의 행동을 결정했습니다.**

<h3 id="experience-adaptation">
  04. 같은 경험을 모든 화면에 그대로 축소하지 않았습니다.
</h3>

반응형을 설계할 때 목표를 **데스크톱 화면을 작은 크기로 그대로 재현하는 것**에 두지 않았습니다. 화면의 크기뿐 아니라 입력 방식과 스크롤 환경이 달라지면, 같은 의도를 전달하는 방법 역시 달라져야 한다고 봤습니다.

모바일은 휠 스크롤과 달리 터치 자체에 관성이 있고, 브라우저 UI 변화에 따라 viewport 높이도 달라질 수 있습니다. 실제 기기에서는 데스크톱의 긴 고정 구간과 복합적인 스크롤 연출을 그대로 적용했을 때 **화면이 떨리거나 손가락의 움직임보다 화면이 늦게 따라오는 경험**이 발생했습니다. 이를 단순한 구현 오류로 보기보다, **모바일에서는 같은 연출 자체가 적합하지 않을 수 있다는 신호**로 봤습니다.

그래서 기준은 **“이 장면을 붙잡아두는 것이 내용을 이해하는 데 정말 필요한가?”**였습니다. 하나의 내용을 단계적으로 이해하기 위해 필요한 고정은 남기되, 탐색이나 이동을 방해하는 고정은 과감히 제거했습니다. 프로젝트 탐색처럼 사용자가 직접 이동하며 살펴보는 영역에서는 `Pin`을 줄이고 일반적인 스크롤 흐름으로 단순화했습니다. **시각적인 풍부함보다 터치와 화면 반응 사이의 직접성을 우선한 선택**이었습니다.

> 같은 화면을 유지하는 것이 아니라, 환경이 달라져도 같은 의도와 흐름을 안정적으로 경험할 수 있도록 다시 설계했습니다.

<h3 id="experience-feedback">
  05. 피드백으로 정보 구조를 바꾸고, 데이터로 검증했습니다.
</h3>

사이트를 배포한 뒤에도 처음 설계한 정보 구조를 완성된 답으로 두지 않았습니다. **제가 자연스럽다고 생각한 흐름과 실제 사용자가 원하는 탐색 방식은 다를 수 있다고 봤기 때문입니다.**

초기에는 제 작업 과정을 하나의 서사로 보여주기 위해 `Build`와 `Projects`를 `Capability` 영역 안에서 함께 구성했습니다. 하지만 현업 피드백을 통해 채용 담당자에게 `Projects`는 흐름 속에서 발견하는 콘텐츠보다 **빠르게 찾아볼 수 있는 독립적인 영역이어야 한다**는 점을 확인했습니다.

이를 반영해 `Capability` 안에 묶여 있던 `Build`와 `Projects`를 분리하고, 각각의 목적에 맞게 독립적인 탐색 영역으로 정보 구조를 재설계했습니다.

변경 전후의 Amplitude 데이터를 동일한 기준으로 비교한 결과, **Contact까지 도달한 사용자 비율은 39.6%에서 48.3%로 8.7%p 증가했습니다.**

![IA 재설계 이후 섹션별 사용자 도달 추이](/images/projects/portfolio/detail/section-reach-analytics.png)

재설계 이후에는 `Intro → Build → Projects → Contact`를 각각 독립적으로 측정할 수 있도록 이벤트 구조도 다시 정리했습니다. 이를 통해 피드백을 반영하는 데서 끝나지 않고, **바꾼 정보 구조가 실제 사용자의 탐색 흐름에서 어떤 변화로 나타나는지 다시 확인할 수 있었습니다.**

> **현업 피드백을 바탕으로 정보 구조를 다시 설계하고, 실제 사용자 행동을 통해 그 변화를 검증했습니다.**

</ProjectDetailSection>

<span id="engineering-runtime" className="project-detail-section__anchor" />

kimbom.dev에는 스크롤에 따라 되감기는 장면, 한 번 나타난 뒤 상태를 유지하는 장면, 화면을 고정한 채 내부 콘텐츠가 바뀌는 장면처럼 **서로 다른 방식으로 동작하는 Animation이 여러 곳에 존재합니다.**

처음에는 각 스테이지마다 필요한 DOM을 찾고, Animation을 만들고, `ScrollTrigger`를 연결하고, 종료할 때 정리하는 코드까지 직접 작성했습니다.

장면이 적을 때는 문제가 없었지만 Animation이 늘어나면서 Stage마다 코드의 실행 순서와 정리 방식이 조금씩 달라졌습니다. 새로운 장면 하나를 추가하려 해도 매번 기존 코드를 읽으며 확인해야 했습니다.

> 어떤 DOM을 먼저 찾아야 하는가?
>
> Animation은 어디에서 만드는가?
>
> ScrollTrigger는 어디에서 연결하는가?
>
> 스크롤 값은 Animation에 어떻게 전달하는가?
>
> 화면이 사라질 때 생성한 자원은 어디에서 정리하는가?

그래서 Animation 자체를 하나로 합치는 대신, **Animation이 만들어지고 실행되고 사라지는 전체 과정을 하나의 공통된 흐름으로 정리했습니다.**

#### Stage Interaction Architecture

아래 구조는 Stage가 화면에 나타난 순간부터 사용자의 스크롤이 실제 Animation으로 전달되고, 마지막에 생성한 자원이 정리될 때까지를 정리한 아키텍처입니다.

![Stage Interaction Architecture](/images/projects/portfolio/detail/stage-interaction-architecture.png)

전체 구조는 크게 **초기화 → 실행 → 정리** 세 단계로 이어집니다.

> **Initialization**
>
> → 실행 환경을 확인하고, 필요한 DOM과 Animation Controller를 준비한 뒤 ScrollTrigger를 연결합니다.

> **Runtime Loop**
>
> → 사용자의 스크롤 위치를 progress로 계산하고, Controller를 통해 Animation에 전달합니다.

> **Lifecycle End**
>
> → Stage가 종료되거나 환경이 바뀌면 Trigger, Controller, Timeline 등 생성한 자원을 정리합니다.

#### Initialization — Stage가 시작되면 Animation 실행에 필요한 환경과 대상을 순서대로 준비합니다.

Stage가 화면에 나타나면 먼저 현재 환경이 Desktop인지 Mobile/Tablet인지 확인하고, 그에 맞는 Scroll 설정을 선택합니다. 화면 크기에 따라 Animation이 시작·종료되는 위치나 `scrub`, `pin` 여부가 달라질 수 있기 때문입니다.

그다음 Animation에 필요한 DOM을 수집합니다. 이때 Stage에서 모든 요소를 한 번에 찾지 않고, **Stage와 Scene이 서로 다른 범위의 DOM을 담당하도록 나눴습니다.**

> **Stage**
>
> → `Intro / Structure / AI / Visual`처럼 ScrollTrigger의 기준이 되는 **Scene Root만 찾습니다.**

> **Scene DOM Helper**
>
> → 자신의 Scene 안에서 `card / text / icon / image`처럼 실제 Animation에 필요한 **세부 요소만 찾습니다.**

예를 들어 Stage는 `AI Scene`이 어디에 있는지만 알고, AI 내부에 어떤 카드와 아이콘이 있는지는 AI Scene의 DOM Helper가 담당합니다.

이렇게 탐색 범위를 나눠 **Scene 내부 마크업이 바뀌어도 Stage의 스크롤 구조까지 함께 수정되지 않도록 했습니다.**

필요한 DOM을 모두 수집한 뒤에는 각 Scene의 Animation Controller를 생성합니다.

Controller는 `ScrollTrigger`와 실제 GSAP Animation 사이에서 값을 전달하는 역할을 합니다. 각 Animation 내부 구현은 달라도 외부에서는 같은 방식으로 사용할 수 있도록 Controller의 형태를 맞췄습니다.

```tsx
type AnimationController = {
  setProgress: (progress: number) => void;
  destroy: () => void;
};
```

Stage는 Animation 내부에서 Timeline을 몇 개 사용하는지, 어떤 easing이나 stagger를 적용하는지 알 필요가 없습니다.

현재 스크롤 상태는 `setProgress()`로 전달하고, Stage가 종료될 때는 `destroy()`를 호출하면 됩니다.

마지막으로 선택한 Scroll Config와 생성한 Controller를 `ScrollTrigger`에 연결하면 초기화가 끝납니다.

```text
Viewport 확인
→ Scroll Config 선택
→ Scene Root 수집
→ Scene 내부 Target 수집
→ Controller 생성
→ ScrollTrigger 연결
```

이렇게 **Animation이 실행되기 전 준비 순서를 통일해**, 새로운 Scene이나 Animation을 추가할 때도 DOM 수집부터 ScrollTrigger 연결까지의 위치를 예측할 수 있도록 했습니다.

#### Runtime Loop — 스크롤 위치를 progress로 바꿔 Animation에 전달합니다.

초기화가 끝난 뒤에는 사용자의 스크롤에 따라 Runtime Loop가 반복됩니다.

`ScrollTrigger`는 현재 스크롤 위치를 감지하고, Animation의 시작점과 끝점을 기준으로 이를 `0 ~ 1` 사이의 progress로 계산합니다.

예를 들어 Animation 구간의 절반까지 이동했다면 progress는 약 `0.5`가 됩니다.

계산한 값은 앞에서 생성한 Controller의 `setProgress()`를 통해 Animation에 전달됩니다.

```text
User Scroll
→ ScrollTrigger
→ progress 계산
→ controller.setProgress()
→ GSAP Timeline
→ DOM Update
```

Controller 내부에서는 전달받은 progress에 맞춰 GSAP Timeline의 진행 상태를 업데이트합니다. 그 결과 `opacity`, `position`, `scale`처럼 실제 화면에 보이는 요소가 스크롤 위치에 따라 변화합니다.

이 구조에서 `ScrollTrigger`는 **현재 어느 정도 스크롤했는지를 계산하는 역할**에 집중하고, Animation은 **전달받은 값으로 화면을 어떻게 움직일지 결정하는 역할**에 집중합니다.

#### 장면마다 progress를 처리하는 방식은 다르게 두었습니다.

모든 Animation이 progress를 전달받는다는 점은 같지만, 스크롤을 되돌렸을 때 어떻게 반응해야 하는지는 장면마다 달랐습니다.

스크롤을 위로 되돌렸을 때 Animation도 함께 되감겨야 하는 장면은 **현재 progress를 그대로 사용합니다.**

반대로 한 번 나타난 콘텐츠가 다시 사라지지 않아야 하는 장면은 **지금까지 도달한 최대 progress를 유지합니다.**

또 `pin`, `activeIndex`, 하나의 progress를 여러 구간으로 나누는 장면처럼 별도의 계산이 필요한 경우에는 공통 Helper에 억지로 넣지 않고 장면별 로직으로 처리했습니다.

> **Reversible** → 현재 progress 사용
>
> **Persist Reveal** → 최대 progress 유지
>
> **Special / Custom** → Pin, Active Index 등 별도 처리

즉 **Scroll → progress → Controller라는 실행 흐름은 동일하게 유지하되, progress를 해석하는 방식은 각 장면의 목적에 맞게 나눴습니다.**

#### Lifecycle End — 생성한 자원을 각 계층에서 직접 정리합니다.

Stage가 화면에서 사라지거나 Desktop과 Mobile 환경이 전환되면 기존에 생성한 ScrollTrigger와 Animation도 함께 정리해야 합니다.

이때 상위 계층이 하위 Animation의 내부 자원까지 직접 찾아 제거하지 않도록 했습니다.

Stage Hook에서 만든 `ScrollTrigger`는 Stage Hook에서 제거하고, Animation Controller가 만든 Timeline은 `destroy()` 내부에서 정리합니다. `matchMedia`와 GSAP Context 역시 자신이 생성한 범위에서 `revert()`합니다.

```text
Stage 종료 / 환경 변경
→ ScrollTrigger 제거
→ Controller.destroy()
→ Timeline 제거
→ GSAP Context 복원
```

즉 **자원을 생성한 위치와 제거하는 위치를 대응시켜**, Stage가 종료될 때 어떤 자원이 어디에서 정리되는지까지 한 방향으로 추적할 수 있도록 했습니다.

#### 핵심

리팩토링 이후에는 Animation의 동작이 서로 달라도 **초기화 → 실행 → 정리라는 lifecycle은 동일하게 유지됩니다.** 새로운 Animation도 정해진 흐름 안에서 DOM, Controller, Trigger를 연결할 수 있어 실행 과정과 수정 위치를 예측할 수 있게 됐습니다.

> **서로 다른 Animation을 같은 방식으로 구현한 것이 아니라, 서로 다른 실행 규칙을 가진 동작을 하나의 예측 가능한 lifecycle 안에서 관리하도록 설계했습니다.**

<h3 id="engineering-safari">
  Safari(WebKit) 환경에서 발생한 레이아웃 문제를 해결했습니다.
</h3>

**Life Motion은 개발 결과물뿐 아니라 저를 구성하는 관심사와 활동, 경험까지 함께 보여주기 위해 만든 파트입니다.** 여러 순간이 계속 이어지는 느낌을 표현하기 위해 이미지 묶음을 연결한 무한 롤링 배너를 구현했고, 그 과정에서 Chrome과 달리 Safari에서는 뒤에 이어져야 할 이미지 그룹이 앞의 그룹과 겹치는 현상이 발생했습니다.

스크롤 Animation이 적용된 영역이었기 때문에 먼저 GSAP의 영향을 확인했지만, 관련 동작을 배제해도 문제가 유지됐습니다. 이후 실제 DOM 크기를 비교하면서 Safari에서 **부모가 계산한 그룹 너비와 내부 카드가 실제로 차지하는 영역이 다르게 나타나는 것**을 확인했습니다.

관련 사례를 조사하면서 **Safari/WebKit에서 Flexbox와 콘텐츠 기반 크기 계산이 함께 사용될 때 발생하는 유사한 Intrinsic Sizing 사례**를 확인했습니다. 기존 구조 역시 자식의 `flex-basis`를 바탕으로 상위 요소의 `max-content` 너비를 다시 계산하는 방식이어서, 브라우저가 여러 단계에 걸쳐 크기를 추론해야 했습니다.

이를 Safari 전용 예외 처리로 우회하지 않고, **자식 카드의 실제 너비와 상위 요소의 콘텐츠 크기 기준을 명시해 크기 계산 과정을 단순화했습니다.** 그 결과 별도의 브라우저 분기 없이 Chrome과 Safari에서 동일한 롤링 레이아웃을 유지할 수 있도록 개선했습니다.

<h3 id="engineering-performance">
  초기 리소스 경쟁을 줄여 LCP를 76% 단축했습니다.
</h3>

모바일 Lighthouse 측정에서 Performance는 **86점, LCP는 4.1초**로 나타났습니다. 초기 화면의 이미지 비중이 높은 사이트였기 때문에 단순히 콘텐츠를 제거하거나 이미지 수를 줄이기보다 **실제 LCP 요소와 초기 네트워크 요청을 먼저 추적했습니다.**

Chrome Performance Panel에서 LCP Marker와 실제 DOM 요소를 확인한 결과, Life Motion의 이미지가 LCP로 측정되고 있었습니다. Network 요청을 함께 살펴보니 **첫 8개 이미지에 모두 높은 로딩 우선순위가 적용되어, 초기 화면에 즉시 필요하지 않은 이미지까지 같은 시점에 요청되고 있었습니다.**

즉 문제는 단순히 “이미지가 많다”는 것이 아니라, **여러 이미지가 동시에 높은 우선순위를 가지면서 초기 리소스 경쟁이 발생한 것**이었습니다.

그래서 반복 이미지에 적용된 `priority`를 제거하고, 화면 크기에 맞는 `sizes`와 이미지 품질을 함께 조정해 **초기 화면에 필요한 리소스가 먼저 로드되도록 우선순위를 다시 구성했습니다.**

그 결과 모바일 Lighthouse Performance는 **86점 → 99점**, LCP는 **4.1초 → 1.0초로 약 76% 단축**되었습니다.

> **콘텐츠를 줄여 성능을 맞추는 대신, LCP 요소와 네트워크 요청 우선순위를 측정해 초기 리소스 경쟁을 줄였습니다.**

<h3 id="impact-engineering">

<h3 id="impact-validation">

> **사용자 피드백으로 경험을 수정하고, 행동 데이터와 성능 지표로 그 결과를 다시 확인했습니다.**
