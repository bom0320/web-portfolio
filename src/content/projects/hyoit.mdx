**‘효도(孝)’ + ‘IT’ = 효잇(Hyoit)**

효잇은 ICT 기술을 통해 물리적으로 떨어진 부모와 자녀의 안부 확인과 일상적인 상호작용을 지원하는 **가족 케어 서비스**입니다. 바쁜 일상 속에서 가족 간 연락이 줄어들고, 관계의 단절이 돌봄의 공백으로 이어지는 문제를 완화하기 위해 기획했습니다.

효잇은 단순한 건강 관리나 감시 중심의 서비스보다 **가족 간 연결을 지속하는 경험**에 집중했습니다. 긴 대화를 시작하지 않아도 짧은 안부 확인과 상태 공유만으로 서로의 상태를 자연스럽게 확인하고, 관계가 일상 속에서 이어질 수 있도록 설계했습니다.

이를 위해 상태 기반 홈 화면, 빠른 응답, 알림 전달과 확인 상태를 중심으로 상호작용을 구성했습니다. 또한 같은 가족이라도 부모와 자녀의 사용 환경과 목적이 다르다고 보고, **하나의 앱 안에서 역할에 따라 화면과 기능 흐름을 분리**했습니다.

특히 부모 사용자의 디지털 환경을 고려해 큰 CTA, 최소 입력 구조, 반복 가능한 인터랙션 패턴과 단순한 화면 흐름을 적용했습니다. 복잡한 기능을 학습하지 않아도 짧은 행동만으로 가족과 연결될 수 있는 경험을 만드는 것을 목표로 했습니다.

<span id="problem-connection" className="project-detail-section__anchor" />

#### 문제는 단순히 혼자 있는 것이 아니라, 지속적인 연결이 줄어드는 데 있었습니다.

바쁜 일상을 보내다 보면 부모님께 연락해야 한다고 생각하면서도 전화는 자연스럽게 미뤄지곤 합니다. 그렇게 연락의 간격이 길어지면 부모와 자녀가 서로의 일상을 확인하는 기회 역시 점차 줄어듭니다.

효잇을 기획하며 고령층의 사회적 고립과 가족 돌봄에 관한 자료를 조사했고, 단순히 독거 여부보다 **사회적 관계망의 축소와 지속적인 상호작용의 부재**가 중요한 문제로 다뤄지고 있다는 점에 주목했습니다. 일본의 Aging in Place 사례에서도 고령층이 익숙한 환경과 관계를 지속적으로 유지하는 것이 중요한 요소로 다뤄지고 있었습니다.

이를 통해 해결해야 할 문제를 단순한 상태 관리가 아니라, **일상 속에서 가족 간 연결을 어떻게 지속할 것인가**로 정의했습니다.

---

<h3 id="problem-care-service">
  02. 기존 돌봄 서비스는 관계 유지까지 해결하지 못했습니다.
</h3>

#### 관리 기능보다 ‘누군가와 연결되어 있다’는 경험이 필요했습니다.

기존의 많은 실버케어 서비스는 건강 데이터 관리, 응급 감지, 위치 추적과 같이 고령층의 상태를 확인하고 관리하는 기능에 집중되어 있었습니다.

이러한 기능은 돌봄에 필요하지만, 그것만으로 가족 간의 지속적인 상호작용이나 정서적인 연결까지 만들어내기는 어렵다고 보았습니다.

관련 자료를 조사하는 과정에서도 고령층 서비스의 만족도에는 기능 자체뿐 아니라 **공감, 반응성, 신뢰, 안심과 같은 관계 기반 경험**이 중요하게 작용한다는 점을 확인했습니다.

따라서 효잇에서는 부모를 일방적으로 관리하는 대상처럼 바라보기보다, **부모와 자녀 모두가 함께 연결 경험을 만들어가는 양방향 구조**를 제품의 방향으로 잡았습니다.

---

<h3 id="problem-family-burden">
  03. 돌봄의 공백은 가족의 부담으로도 이어지고 있었습니다.
</h3>

#### 계속 확인해야 하는 상태 자체가 새로운 부담이 될 수 있었습니다.

부모와 떨어져 생활하는 자녀에게도 돌봄은 지속적인 부담이 될 수 있습니다.

부모님의 상태가 괜찮은지 신경 쓰고, 연락이 없으면 다시 확인하고, 응답을 기다리는 과정은 단순한 물리적 돌봄을 넘어 **계속 신경 써야 하는 상태**를 만들 수 있었습니다.

가족 돌봄과 사회적 고립을 다룬 자료에서도 돌봄 시간이 길어지고 책임이 한 사람에게 집중될수록 심리적인 피로와 스트레스가 커질 수 있다는 점을 확인했습니다.

그렇다고 연락을 더 자주 하도록 요구하는 것은 또 다른 부담이 될 수 있었습니다.

그래서 필요한 것은 더 많은 관리 기능이 아니라, **복잡한 입력이나 긴 대화 없이도 서로의 상태를 확인할 수 있는 구조**에 가깝다고 판단했습니다.

---

<h3 id="problem-continuous-connection">
  04. 그래서 지속적인 연결 경험에 집중했습니다.
</h3>

#### 긴 대화를 요구하기보다, 짧은 행동으로 관계를 이어가도록 했습니다.

효잇은 단순한 메신저나 관리 서비스가 아니라, **가족 간 관계 유지 행동 자체를 설계하는 서비스**를 목표로 했습니다.

전화나 긴 메시지를 시작하지 않아도 빠른 응답 버튼으로 안부를 전하고, 상태 기반 알림과 읽음·확인 여부를 통해 서로의 상태를 자연스럽게 확인할 수 있도록 구성했습니다.

또한 부모와 자녀의 사용 목적을 하나의 화면에 맞추지 않고 역할별 UX를 분리했으며, 고령층 사용자는 큰 CTA와 최소 입력, 단순한 흐름을 통해 복잡한 기능 학습 없이도 서비스를 사용할 수 있도록 설계했습니다.

결국 효잇이 해결하고자 한 것은 **“어떻게 더 많이 연락하게 할 것인가”가 아니라, “어떻게 부담 없이 연결을 계속 이어갈 수 있게 할 것인가”**였습니다.

<span id="experience-status-home" className="project-detail-section__anchor" />

#### 사용자가 지금 확인해야 할 정보를 한눈에 파악하도록 구성했습니다.

효잇의 홈 화면은 여러 기능을 단순히 나열하기보다, **현재 사용자의 상태와 필요한 행동을 먼저 확인할 수 있는 구조**를 중심으로 설계했습니다.

![안부 상태에 따라 달라지는 효잇 홈 화면](/images/projects/hyoit/detail/home-status-flow.png)

사용자는 홈에서 최근 알림 상태, 가족 연결 여부, 안부 확인 필요 상태 등을 우선적으로 확인할 수 있습니다. 새로운 안부가 도착하거나 확인이 필요한 경우에는 상단 상태 배너를 통해 현재 상황을 먼저 보여주고, 안부 확인이나 빠른 응답 행동으로 바로 이동할 수 있도록 구성했습니다.

안부 상태 역시 하나의 화면으로 고정하지 않고,

**안부 없음 → 새 안부 도착 → 안부 확인 → 새 안부 누적**

과 같이 현재 상태에 따라 상단 배너와 최근 안부 영역이 달라지도록 설계했습니다.

이를 통해 사용자가 별도의 메뉴를 탐색하지 않아도 **지금 확인해야 할 안부가 있는지, 이미 확인한 상태인지, 새로운 안부가 추가되었는지**를 홈에서 바로 판단할 수 있도록 했습니다.

또한 효잇을 안부가 필요할 때만 사용하는 앱으로 만들기보다, 일상 속에서 자연스럽게 반복 접근할 수 있는 구조도 함께 고려했습니다.

날씨 정보와 D-Day, 카드 맞추기 게임처럼 가볍게 확인하거나 참여할 수 있는 요소를 홈 경험과 연결했습니다. 특히 카드 맞추기 게임은 복잡한 조작 없이 쉽게 참여할 수 있도록 단순한 인터랙션을 적용해 고령층 사용자도 부담 없이 사용할 수 있도록 구성했습니다.

<h3 id="experience-quick-response">
  02. 짧은 반응만으로 안부를 주고받도록 설계했습니다.
</h3>

#### 긴 대화와 직접 입력에서 발생하는 부담을 줄였습니다.

일반적인 메신저는 직접 문장을 입력하고 대화를 이어가는 방식을 중심으로 합니다.

하지만 고령층 사용자에게 긴 입력은 조작 부담이 될 수 있고, 부모와 자녀 모두에게 매번 새로운 대화를 시작해야 한다는 부담이 생길 수 있다고 보았습니다.

![안부 확인 전후와 누적 상태를 보여주는 효잇 안부 흐름](/images/projects/hyoit/detail/quick-reply-flow.png)

효잇에서는 이를 줄이기 위해 자주 사용하는 안부 표현을 버튼 형태로 제공했습니다.

- `잘 지내고 있어요 😊`
- `사랑해~ 💕`
- `밥 잘 먹고 다녀 🍚`
- `통화 한번 해 📞`

처럼 짧은 선택만으로도 안부를 전달할 수 있도록 하고, 필요할 경우 직접 입력도 선택할 수 있도록 구성했습니다.

상태 응답 역시 `"괜찮아요"`, `"조금 불편해요"`, `"연락해주세요"`처럼 선택 중심으로 구성해 사용자가 자신의 상태를 긴 문장으로 설명하지 않아도 전달할 수 있도록 설계했습니다.

안부를 보내는 것으로 상호작용이 끝나지 않도록 **최근 알림과 읽음·확인 여부도 함께 제공**했습니다.

부모와 자녀가 상대방이 안부를 확인했는지 다시 묻지 않아도 상태를 파악할 수 있도록 하고, 푸시 알림을 통해 새로운 안부도 빠르게 확인할 수 있도록 구성했습니다.

결과적으로 효잇에서는 더 많은 대화를 요구하기보다, **짧은 행동만으로도 서로를 확인하고 연결을 이어갈 수 있는 상호작용**을 만드는 데 집중했습니다.

<h3 id="experience-role-based">
  03. 부모와 자녀의 경험을 역할별로 분리했습니다.
</h3>

#### 같은 서비스를 사용하더라도 필요한 정보와 행동은 다르다고 판단했습니다.

효잇은 부모와 자녀가 함께 사용하는 양방향 가족 케어 서비스입니다.

기존 실버케어 서비스처럼 부모만을 관리 대상으로 두기보다, **부모와 자녀 모두가 하나의 연결 관계 안에서 서비스를 사용할 수 있는 구조**를 목표로 했습니다.

다만 같은 가족이라고 해서 두 사용자에게 동일한 화면과 기능을 제공하지는 않았습니다.

부모와 자녀는 앱을 사용하는 목적과 디지털 환경이 다르다고 보고, 온보딩에서 역할을 선택한 이후 각 역할에 맞는 UX 흐름으로 분기되도록 설계했습니다.

부모 사용자는

- 단순한 화면 흐름
- 큰 인터랙션 요소
- 최소 입력 구조
- 빠른 안부 응답

을 중심으로 사용할 수 있도록 구성했습니다.

반면 자녀 사용자는

- 부모 상태 확인
- 안부 전달
- 일정 및 D-Day 관리
- 가족 연결 상태 확인

처럼 **정보를 빠르게 확인하고 필요한 행동으로 이동하는 흐름**을 중심으로 구성했습니다.

부모와 자녀는 6자리 연결 코드를 통해 가족 관계를 형성하고, 이후 안부와 상태, 알림 등의 정보를 양방향으로 주고받습니다.

즉, **가족이라는 하나의 관계는 공유하되 사용 경험은 역할에 맞게 분리**하는 것을 UX 구조의 기준으로 삼았습니다.

---

<h3 id="experience-senior-ux">
  04. 고령층의 조작 부담을 줄이는 UX를 적용했습니다.
</h3>

#### 복잡한 기능을 학습하지 않아도 사용할 수 있는 흐름을 지향했습니다.

고령층 사용자는 작은 버튼이나 복잡한 화면 구조, 긴 입력 과정에서 높은 조작 피로와 사용 부담을 경험할 수 있습니다.

효잇에서는 이를 고려해

- 큰 CTA 버튼
- 최소 입력 구조
- 반복 가능한 인터랙션 패턴
- 명확한 상태 중심 UI
- 2~3단계 이내의 단순한 흐름

을 주요 UX 기준으로 적용했습니다.

주요 행동은 직접 입력보다 선택을 중심으로 구성하고, 화면마다 새로운 인터랙션을 학습하지 않아도 되도록 반복되는 패턴을 사용했습니다.

![로그인부터 역할 선택까지 이어지는 효잇의 단순한 진입 흐름](/images/projects/hyoit/detail/senior-friendly-flow.png)

또한 과도한 선택지와 빠른 화면 전환을 줄이고, 사용자가 현재 상태와 다음 행동을 쉽게 구분할 수 있도록 화면 구조를 단순화했습니다.

카드 맞추기처럼 앱 내에서 반복적으로 사용하는 기능 역시 복잡한 규칙이나 조작보다 단순한 터치 중심의 인터랙션으로 구성했습니다.

효잇에서 시니어 UX는 단순히 화면 요소를 크게 만드는 것이 아니라, **사용 과정에서 요구되는 입력과 판단, 학습의 부담을 줄이는 방향**으로 적용했습니다.

#### 재사용 여부보다 코드가 어떤 이유로 변경되는지를 기준으로 모노레포를 구성했습니다.

효잇은 하나의 모바일 앱 안에서 부모와 자녀라는 서로 다른 사용자 경험을 함께 제공합니다.

기능이 늘어나면서 두 역할이 함께 사용하는 코드도 많아졌지만, **여러 곳에서 사용된다는 이유만으로 모든 공통 코드를 하나의 영역에 모으면** 앱 전체의 기반 코드와 효잇의 특정 사용자 경험에 종속된 코드가 섞일 수 있다고 판단했습니다.

이에 pnpm Workspace 기반으로 모바일 앱과 공통 패키지를 분리하고, `apps/mobile` 내부에서도 부모·자녀·공통 영역을 나누는 구조로 개발하고 있습니다. 현재 저장소에서도 `apps/mobile`과 `packages/auth`, `storage`, `types`, `ui`가 분리되어 있습니다.

```text
hyoit-FE
├─ apps
│  └─ mobile
│     └─ src
│        ├─ parent
│        ├─ child
│        └─ shared
│
└─ packages
   ├─ auth
   ├─ storage
   ├─ types
   └─ ui
```

구조를 나눌 때 사용한 핵심 기준은 다음 질문이었습니다.

> **“효잇의 모바일 화면을 몰라도 이 코드의 역할을 설명할 수 있는가?”**

`Button`, `Card`, `UserRole`, 인증 상태, Storage Wrapper처럼 특정 화면이나 부모·자녀 흐름을 몰라도 역할이 설명되는 코드는 `packages`에 둡니다.

반대로 홈 상태, 역할별 문구, 부모 홈의 자녀 카드, 안부 응답처럼 **효잇의 화면과 사용자 흐름을 알아야 의미를 설명할 수 있는 코드**는 `apps/mobile/src` 내부에서 관리합니다.

그 안에서도 변경 이유에 따라 다시 경계를 나눴습니다.

- `parent` — 부모 사용자 경험 때문에 변경되는 코드
- `child` — 자녀 사용자 경험 때문에 변경되는 코드
- `shared` — 부모와 자녀가 함께 사용하지만 모바일 제품 맥락을 가지는 코드
- `packages` — 특정 화면이나 역할과 무관한 앱 기반 코드

즉, **“같이 쓰이니까 공통화한다”보다 “같은 이유로 변경되는 코드끼리 묶는다”**는 기준으로 구조를 확장하고 있습니다.

현재도 기능을 추가하면서 이 기준에 따라 각 코드의 위치와 책임을 조정하고 있으며, 역할별 제품 로직과 앱 기반 코드의 경계가 흐려지지 않도록 구조를 계속 다듬고 있습니다.

<h3 id="engineering-entry">
  02. 화면마다 분기하지 않고, 사용자 상태로 진입 경로를 결정했습니다.
</h3>

#### 인증 여부와 역할을 하나의 Entry 정책으로 모아 부모·자녀 흐름을 분리했습니다.

효잇은 로그인 이후 모든 사용자가 같은 홈으로 진입하는 구조가 아닙니다.

로그인하지 않은 사용자는 인증 화면으로 이동해야 하고, 로그인했지만 역할을 선택하지 않았다면 역할 선택 과정이 필요합니다. 역할이 결정된 이후에는 부모와 자녀가 서로 다른 화면 흐름으로 진입해야 합니다.

이를 각 화면에서 개별적으로 판단하면 인증과 역할에 대한 조건문이 여러 라우트에 반복되고, 새로운 사용자 상태가 추가될수록 진입 규칙을 추적하기 어려워질 수 있다고 보았습니다.

그래서 인증 상태와 사용자 역할을 Zustand의 `useAuthStore`에서 관리하고, 별도의 `resolveEntryTarget`에서 현재 사용자가 이동해야 할 영역을 결정하도록 구성했습니다. 현재 Store에는 로그인 여부, `role`, 부모·자녀별 온보딩 상태가 명시적으로 관리되고 있습니다.

```text
App Entry
   ↓
Authenticated?
   ├─ No  → Login
   └─ Yes
       ↓
     Role?
       ├─ None   → Choose Role
       ├─ Parent → Parent Flow
       └─ Child  → Child Flow
```

실제 Entry에서는 화면 이동 조건을 직접 조합하지 않고,

```text
authenticated + role
        ↓
 resolveEntryTarget
        ↓
login / choose / parent / child
```

형태로 목적지만 결정한 뒤 Expo Router의 Route Group으로 연결합니다. 현재 앱 역시 `(entry)`, `(parent)`, `(child)` 영역이 분리되어 있습니다.

`resolveEntryTarget` 역시 인증되지 않았다면 `login`, 역할이 없다면 `choose`, 이후에는 `parent` 또는 `child`를 반환하는 작은 정책 함수로 분리되어 있습니다. 실제 루트 화면에서는 이 결과만 받아 각 Route Group으로 Redirect합니다.

이를 통해 **“어떤 화면에서 어디로 이동할 것인가”와 “현재 사용자 상태라면 어디에 있어야 하는가”를 분리**했습니다.

현재는 인증 여부와 역할을 중심으로 Entry 정책을 구성하고 있으며, 부모·자녀별 온보딩 상태도 Store에서 별도로 관리하고 있어 이후 가족 연결과 온보딩 흐름이 확장되는 과정에서 진입 정책 역시 함께 발전시키고 있습니다.

<h3 id="engineering-routing">03. 라우팅과 화면 구현의 책임을 분리했습니다.</h3>

#### Expo Router의 `app`은 진입점으로만 두고, 실제 화면 구현 위치를 하나로 정리했습니다.

효잇의 초기 구조에서는 Expo Router의 `app`과 `src/*/pages`, `widgets`에 화면 관련 코드가 함께 존재하면서 **어디까지가 라우팅이고 어디부터가 실제 화면 구현인지 경계가 불명확했습니다.**

기능이 추가될수록 동일한 화면을 수정할 때 여러 계층을 함께 확인해야 했고, 부모·자녀 흐름이 확장될수록 화면 구현 위치를 예측하기 어려워질 수 있다고 판단했습니다.

이에 Expo Router의 `app` 디렉터리는 **URL과 Route Group을 연결하는 진입점 역할만 담당**하도록 정리하고, 실제 화면 구현은 역할별 `widgets/*-page`에서 관리하도록 구조를 변경했습니다.

```text
app
├─ (entry)
├─ (parent)
└─ (child)
    ↓
Route Entry

src
├─ entry/widgets/*-page
├─ parent/widgets/*-page
└─ child/widgets/*-page
    ↓
Actual Screen
```

라우트 파일에서는 화면을 직접 구현하지 않고 해당 역할의 Page Widget만 연결합니다.

```tsx
export default function HomeRoute() {
  return <HomePage />;
}
```

부모·자녀 온보딩처럼 여러 단계로 구성되는 화면 역시 Page Widget 내부에서 각 Screen 단위로 나누어, **라우팅 계층과 실제 사용자 흐름을 구현하는 계층의 책임이 섞이지 않도록** 했습니다.

이를 통해 `app`은 **어디로 진입하는지**, `src`는 **그 화면에서 무엇을 보여주고 어떻게 동작하는지**를 담당하도록 구조의 기준을 명확하게 만들었습니다.
